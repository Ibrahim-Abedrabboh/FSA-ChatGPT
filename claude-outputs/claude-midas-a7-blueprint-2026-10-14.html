Controlled workflow or one agent

Both designs share six foundations: the original identity, a versioned contract, genuine Midas references, evidence-based review, bounded spend and a complete-package gate. They differ in who chooses the next action.

A · Surgical replacement · recommended for A7

Code chooses; models perform

  • Predictable steps, small prompts, cost bounds you can inspect, stable recovery.
  • The reviewer is a separate call, and in A7 a different model family from the planner.
  • Fits n8n: every step is a node or a small sub-workflow.
  • Risk: brittle on new kinds of input. A7 answers that with the Evidence loop: hold and ask, never guess.

B · One agent with backend rules · not for now

One agent does everything

  • Better at ambiguous briefs and exploring compositions.
  • Reviews its own images. The source calls this "self-review" and says it is not independent.
  • More turns, longer context, harder to bound cost. It costs more in every control trace below.
  • Not built. The sources say a hybrid is "a result to earn through comparison".

Recommendation. Build A7 as Architecture A. Try B, or an A/B hybrid for difficult compositions, only after the anchor set (step 18) shows it wins on false approvals and cost per accepted package.

The A7 workflow

Six stages hand one record to the next. Red hexagons are holds and reconciliation; gold rounded boxes are the owner's decisions. Repairs go back to stage 04, missing evidence goes back to stage 01, and nothing reaches the client as "Approved" without the owner.

01Intake & observeRead every file and the request; record what is seen, what is supplied and what is unknown.
02Compile scopeChoose the route, set what is locked and what may change, and stamp a versioned contract.
03Retrieve & stylePick genuine Midas pieces and plan each image; the owner gives the first go.
04Compile & dispatchWrite each image request, choose the model, reserve the cost and make the image.
05Critique & correctCheck counts and identity first, style second; repair one defect at a time, at most twice.
06Package & releaseAssemble every required output, record the owner's decision and the cost.

Five loops and when to build each

Each loop has a trigger, a limit and a stop. Four run inside a job; the Evaluation loop runs outside live jobs. All five follow the same correction rules: re-attach the original every time, repair only the named defect, check untouched areas again, reject new regressions, stop when evidence is missing or a limit is reached.

The responsibility that cannot disappear at deployment

Brain → steps 7, 8, 9

Interpret the request, reconcile counts and conflicts, set the locks, choose the composition, plan the outputs.

Operator → steps 13, 14, 15, 21

Attach references, write and submit the request, choose the model, check status, keep candidates, export files, count cost.

Critique → steps 16, 17, 18

Compare originals and results, name defects, keep style separate from identity, pick repair targets, stop sequences that do not resolve.

Chat box, refine and variations

What the sources show

  • The target client page has no chat box. Refinement is a form field ("Custom prompting") and the Variations outcome.
  • The arafat preview has one: six chips (Accessories, Spaces, Views, White background, Lighting, Variations). Each message makes a new version with its own cost confirmation. Variations need an approved parent.

Effect on the workflow

  • A message never edits an image in place. It creates a child job: brief v+1 linked to the parent, one changed axis, all other locks carried.
  • Old plans and reviews for that job are voided; the parent's results stay as history.
  • Cost and checks are the same as a new job. Free-text chat must pass step 1 like any instruction.

What the client page needs

  • Phase 2: a "Refine" panel on each result: the chips, one short note, a plan preview, then confirm.
  • Phase 3: a chat box on the same mechanism, once refine works.
  • No internal or provider names; "Generated image" labels; "Approved" only from the owner.

Several products, rooms and spaces

Several products

  • Several photos of one item are one item. They are references with roles, not extra products.
  • A batch is N jobs, each with its own route, checks and package. A towel, a lamp and a dining set never share one image.
  • One scene with several products is New Composition: an inventory list with a count per item, and every item counted by the blind counters.
  • Midas supporting pieces come from the SKU picker or the catalogue table, each with its photo.
  • "Multi-agent" in n8n means parallel sub-workflow runs per item, one controller each, not agents talking to each other. A batch run splits items, runs them with a concurrency limit under the daily cap, then joins the packages.

Existing rooms

  • The client uploads the room with the role Room / target space.
  • Step 6 records room locks: walls, windows, floor, camera and objects that must stay.
  • Step 8 allows changes only to the named pieces. Step 16 checks the room did not change.
  • No room measurements: scale stays "not confirmed" unless the client gives dimensions.

Creating and reusing a space

  • New styled space: the client describes a room; A7 plans it around the required pieces. Output: a room image and the plan.
  • Reuse: today the only stated path is a previous generation or a saved project ("Reuse the accepted space").
  • Proposal, not in any source: a saved-spaces library per project. An owner-approved room image becomes a target_room reference other jobs can pick. Your decision.
