# A7 source understanding and route boundary (local design, not deployed)

This document describes the integration needed to show product, physical piece and room observations in Step 2 for all three routes. Local code includes the pure contract, an owner-scoped endpoint, durable Blob-backed claim/receipt/confirmation storage, a Step 2 review card and a production adapter guarded by `A7_ANALYSIS_READY`. The switch must remain off until the analysis-only n8n path and main continuation are validated and published together. No live n8n workflow uses this entry yet.

## Shared sequence

1. Save an owner-scoped draft and immutable original reference records (ID, role, SHA-256, MIME, bytes). Keep product, other view, room and inspiration roles distinct. The primary original is identity authority; an earlier result can only guide continuity unless an explicit result-edit target is chosen.
2. Ask separately for a bounded paid **analysis** authorization under the selected aggregate job ceiling. This is earlier than the existing generation authorization; it does not create an additive allowance. Use an idempotent operation key and durable claim/receipt; reconcile an uncertain receipt before retrying. Never silently advance to generation, planning or Go 1.
3. The n8n analysis-only boundary runs product Eye, independent count and conflict checking. Run Room reader against a typed room reference when present. If a product photo contains a meaningful room, a separate bounded room-from-product-photo output is needed; the present Room reader only runs for a room reference. Store the raw answers and owner-scoped ledger operation IDs, then project bounded observations. Verify that reader receipts actually belong to this owner, draft and original hashes before creating `analysisReceipt`; string metadata alone is insufficient proof.
4. Present category, physical item count, modules versus seats, item roles, uncertainty, and room features in Step 2. Show side views as views, not additional pieces. Never assert precise dimensions from a photo. Require confirmation or correction of disputed counts, type and room facts. Preserve the observation and the owner's resolution separately.
5. Persist the confirmation with draft version, all relevant original hashes, receipt fingerprint and timestamp. Any reference, version, correction or instruction change invalidates dependent analysis, estimate and plan. The plan must consume the confirmed facts and may not overwrite them with generated-image guesses. Re-estimate after any changed scope; retain Go 1, budget and review gates.

## Asynchronous analysis (18 Oct 2026)

The reads take longer than an owner request can wait, so Analyze no longer runs them inside that request:
1. `POST /api/owner/source-understanding/:id {action:'analyze'}` checks the quote, records a claim marked `background`, starts the background function and answers `202` with `analysis: 'running'`.
2. `netlify/functions/owner-source-analysis-background.mjs` (`config.background`, up to 15 minutes) authenticates the same owner session, takes a one-time `dispatch` marker before any paid call, and waits up to 170 s for the bridge. A repeated start, a platform retry or a second invocation finds the marker and does not read again.
3. The page polls with `recover` every 10 s for up to five minutes. `recover` reads the ledger only; if the start was lost (no marker yet), it starts the background function again, still at most once.

A claim made before this change has no `background` mark and is never dispatched again, because its reads may already be paid; recover it from the ledger as before.

## Inherited analysis for edits (19 Oct 2026, edit phase 2.2)

A saved edit (a version with a parent) that has no analysis of its own reuses its parent's confirmed analysis when its product photo and room photo have the same SHA-256 as the parent's. Nothing is copied or stored: `state()` works the inheritance out on each read, so it ends as soon as a photo differs. It follows a chain of edits back to the version that paid for the reads, which is called the origin. Rules:
- A draft with its own claim always uses its own analysis. An inherited draft refuses a new paid analysis with `analysis_inherited`.
- `requireConfirmedSource` checks the confirmation against the origin draft. The proof names it in `inheritedFrom`.
- `claimSourceContinuation` verifies the paid answers in the origin run's ledger. It still checks the edit's own budget, and the proof still names the edit's own run, so A7's continuation check is unchanged.
- The parent's conflict-check answer (instruction locks) carries over. The edit's own change and keep lines reach A7 through `body.edit` and the 08 edit locks.

## Edit from an approved image (19 Oct 2026, edit phase 2.4)

An edit draft that names an approved image (`resultAssetId`) sends that image's receipt to A7 as `body.edit.base`: the parent run, the output, the Drive file ID and the SHA-256. `editBase` sends it only when the image is one of this owner's recorded images of the parent version and comes from the parent version's own run; otherwise dispatch answers `result_asset_required` (409) and nothing is sent. The site never vouches for the image beyond that:
- A7 01 refuses a receipt whose run is not the job's parent run, and plans one image (`edit_1`) instead of a new package.
- After go 1, A7 E2 checks the receipt against the parent run's own record: the owner's approval of that file and checksum, the same product photo, the parent's white master, and the parent's scene ticket for that image. Any mismatch holds the run before a paid call.
- 19d2 and 19e2 check the master and the approved image against their checksums before the paid call, as for any scene.
- The review compares the result with the approved image (`unchanged_from_base`) as well as with the vendor photo, which still decides the product.
